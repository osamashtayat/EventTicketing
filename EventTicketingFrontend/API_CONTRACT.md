# Frontend API contract

The canonical backend contract is maintained in:

- [Full API reference](../docs/FRONTEND_API.md): methods, bodies, status codes, filters, and permissions.
- [Wire types](../docs/frontend-api.ts): request/response shapes.
- [Business rules](../docs/BUSINESS_RULES.md): scheduling, ownership, inventory, and cancellation.
- [Pending frontend adoption](../docs/FRONTEND_HANDOFF.md): venue capacity, organizer IDs, and My events.

Runtime frontend types/decoders live in each src/features module. They are not
automatically generated by changes to the reference wire types. Verify backend
controllers/DTOs if generated OpenAPI omits actual response codes or custom metadata.

## Integration requirements

- Base URL: VITE_API_BASE_URL, normally https://localhost:7209 in development.
- CORS frontend origin: http://localhost:5173. Production uses explicitly configured origins.
- Opaque bearer authentication; current-user information comes from /api/auth/me.
- Successful payloads are DTOs directly, not Result wrappers. Handle empty 200/201/204.
- Standard list responses are paged; event availability is an unpaged array.
- PUT requires all write fields and an ID matching the route. No PATCH API exists.
- Decode JSON errors as arrays/dictionaries/bodyless responses according to HTTP status.
- Treat suffixless event date strings as UTC. Calendar-only end-day inputs are inclusive;
  response end instants are exclusive. Do not apply that conversion twice on save.
- Preserve numeric money at the JSON boundary. Frontend decimal strings must be
  encoded back to numeric tokens for category writes.
- Booking creation has no idempotency. Disable automatic mutation replay and retain
  unknown-outcome recovery. Cancellation uses owned booking item IDs and cumulative
  cancelledQuantity; omitted Items means full cancellation.

## API support versus current UI

The API supports full venue editing with capacity returned, event owner identification,
and a protected paged /api/events/mine. The current frontend has not yet adopted those
fields/routes. Follow the handoff rather than showing an unavailable API feature or
fabricating capacity/ownership from another public response.

Payments, seats, QR/issued tickets, expiring holds, account listing/promotion, and a
custom logout/revoke endpoint are not available. Do not invent those operations or
silently change backend behavior to complete a frontend screen.
